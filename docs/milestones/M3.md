## Design in one paragraph

Each stored model has a `TableSpec` (table name, key, queryable columns with types and foreign keys, unique sets, append-only flag). The SQL schema, the in-memory index columns and the migration parity test are all derived from those specs, so adding a table for a later milestone is one spec plus one migration. A row is a JSON document (canonical, validated by Pydantic on read and write) plus real columns for everything that is filtered, sorted or summed, plus `rev` (optimistic concurrency) and `schema_version`. League code sees only `persistence.ports`: repositories (`get`, `save(expected_rev=)`, `find(criteria, order_by=)`, `count`, `total`), the append-only ledger and event log, `UnitOfWork` (`with uow: ...; uow.commit()`, rollback on exit) and `WorldReader`.

## Deviations from the design

1. **Core tables, not declarative ORM classes**: one set of specs drives everything; Alembic autogenerate works from the Core metadata.
2. **Tables for entities that do not exist yet** (player season stats, development journal, a reserved `clb_outside` club) are left to M9-M11, each with its own migration; `0001` covers every model present in M1/M2 including the transfer entities.
3. `contracts` is not a table: the contract is part of the player document and its wage/club are real columns of `players`.
4. The in-memory backend does not enforce foreign keys (the SQLite one does); integrity is also covered by `verify_world`.
5. `matches` stores the whole `Match` including both team sheets as the JSON document; events are stored as a `StoredEvent` wrapper (columns `match_id`, `seq`, `type`, `tick`) because `MatchEvent` is a union, not a model.
6. The ledger has no `ref_type/ref_id` filter beyond the first key of `ref`.
7. `UnitOfWork` is an abstract base class (nominal typing) rather than a Protocol, so implementations get the repository attributes checked by mypy.
8. The generated migration is split into small functions so the repo's statement limit applies to it like any other code.

## Not verified

- Concurrent writers (two processes) are not exercised; `rev` checks are tested single-process.
- Performance of large histories (20 seasons of ledger and events) is deferred to M9/M14.
